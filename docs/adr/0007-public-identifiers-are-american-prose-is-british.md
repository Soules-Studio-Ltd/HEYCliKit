# Public identifiers are American, prose is British

Every identifier in the package uses American spelling, in the library and in the test support product alike: types, cases, methods, properties and argument labels, private and internal names, and test function names. That way the code reads naturally beside the Swift standard library and Foundation, which every app calling the package already sits next to, such as `localizedDescription` and `JSONSerialization`. Everything written as prose, doc comments, test display names, the glossary, the changelog and the decision records, stays British, so a doc comment still speaks of an unrecognised line. Where Swift itself departs from American spelling, the package follows Swift, so a cancelled task is `cancelled` as in `Task.isCancelled` and `CancellationError`. Fixture file names are not covered by this rule: a fixture is named after what it captures, in lower case words joined by hyphens, as the fixtures README describes. Only one public identifier had to change to reach this: the watch line case for a line the package cannot read, which was `unrecognised(rawText:)` and became `unrecognized(rawText:)` in 0.5.0. Internal names can be renamed at any time, but public ones cannot, and they are why this is recorded: reversing the rule is a source break for every app that names an identifier it touches.

## Considered options

- British identifiers throughout. Rejected. An app mixes the package's names with Apple's on every line, and a spelling that differs from the frameworks around it reads as a typo and gets typed wrong.
- American everywhere, prose included. Rejected. The prose is written in British English, and switching it would churn every document for no gain to a caller, who never has to type a word of it.
- No convention. Rejected. The package already had both spellings in its public surface, and without a rule each new name reopens the question, while every later correction is another source break.
