# The runner holds a child to ceilings and escalates termination

A `hey` that misbehaves could take the app down with it. The runner read each stream into a `Data` with no end, split watch lines out of a tail with no end, buffered the watch without bound twice over, once in the runner and once in the client, and stopped a child with a bare SIGTERM that a child was free to ignore for ever. None of that needs a malicious CLI. A build that loops printing, a server that sends one enormous line, or an app that stops reading its watch for an afternoon is enough. So every child is now held to three ceilings and every stop escalates, and the numbers live in one internal value, `RunnerLimits`, passed to the live runner and to the client rather than kept in a mutable global, since Swift Testing runs suites in parallel and an override one suite set would race another's.

The numbers are 32 MiB of output per stream, 64 KiB per watch line, 1024 watch lines on the stream the app reads with 4096 raw lines on the runner's stream behind it, and a 5 second grace between SIGTERM and SIGKILL. The measurements behind each one, and the worst case each bound can hold, are set out under the numbers and their measurements, below. In short: the largest captured envelope is 118 KB for 50 postings and the largest captured watch line is 1957 bytes, so both ceilings sit hundreds or tens of times above anything the CLI has been seen to print, and a page size in the low thousands is still well clear of the output ceiling. The 4096 is set well above the 1024 so the replayed lines a watch started with a since date prints cannot trip it, and it has not been measured against a real replay. Watch fell behind carries 1024 whichever of the two buffers filled, so one case never carries two numbers, and the number is true either way: a full runner buffer means more than 1024 lines were waiting unread.

Passing a ceiling is loud, and never a short answer. Cutting a read short quietly is worse than no ceiling at all: an envelope cut short either fails to decode, which is survivable, or decodes into something structurally valid and short, a page presented as a whole one. A partial watch line is the same mistake, a change reported that the CLI never printed. So output too large, line too large and watch fell behind are each a case of `HEYCliKitError`, told apart from a CLI failure and from a decoding failure, and each carries the ceiling that was passed as a plain number.

A watch whose reader falls behind keeps what it already holds and drops the line that does not fit, which is `bufferingOldest` rather than `bufferingNewest`. The app then holds a true prefix of what the CLI printed before the stream fails, rather than a stream with a hole in it whose first casualty could be the `ready` everything after it depends on. The package does not synthesise a `resync` to paper over the hole: it fabricates nothing, and the app restarts the watch with a since date.

A read that passes a ceiling terminates the child at that moment, from inside the Dispatch closure doing the read, and then reads on to end of file keeping nothing. Both halves are needed. A read that simply stopped would leave the child blocked writing into a full pipe, so it would never exit and neither the other stream nor the exit status would ever arrive. A read that discarded to end of file and left terminating to whoever it returned to would never return for a child that prints for ever, since that child never reaches end of file, so nobody would ever send the signal. The Dispatch call is still the last statement before a continuation, so ADR 0004 is unchanged.

Stopping a child sends SIGTERM and then, from a detached `Task` that sleeps for the grace, SIGKILL if the child's ending has still not arrived. It is a task rather than a Dispatch timer so ADR 0004's exceptions stay two, and nothing awaits it, so the grace costs no caller anything. This is not a timeout. Nothing puts a deadline on a call, which remains a decision of its own (ADR 0002): the escalation bounds how long a child outlives a stop that has already been asked for. The ending is sampled a second time before SIGKILL, which reopens the window ADR 0002's addendum and `terminateChild` already describe, where Foundation has reaped the child and not yet handed its status over, once more a grace later. It is left open for the same reason as the first time.

Login's stdout is discarded at the spawn rather than read into a bounded buffer. The package never reads it, so a bound there would terminate a sign in for printing too much and `LoginFailure` has no field to say why: the app would see a bare SIGTERM, which is a ceiling passed in silence, the one thing this decision is meant to rule out.

## The numbers and their measurements

All of them live in `RunnerLimits`, and a test lowers one for the single runner it builds. Passing any of them terminates the child at that moment, from inside the read, which then carries on to end of file keeping nothing.

- **Output ceiling, 32 MiB** per stream per child: stdout on a one shot command, and stderr on every spawn. One byte more throws output too large. The largest captured envelope is `imbox.json`, 118 KB for 50 postings, about 2.4 KB a posting, so 32 MiB is about 14,000 postings of that size and hundreds of times anything the CLI has been seen to print. That is also the practical ceiling on a page size. Postings with longer summaries or more contacts carry more bytes each, so a page size in the low thousands is well clear of it, and a page size near ten thousand is a request that may throw output too large rather than one that is quietly cut. A one shot run that was both cancelled and too large reports the cancellation, which is checked first. A watch child whose stderr passes the ceiling ends the stream with output too large rather than with the signal the package sent it. A sign in whose stderr passes it is terminated and reported not completed with no stderr.
- **Line ceiling, 64 KiB** per line of a watch's stdout, not counting its newline, checked while the line is still growing, so a child that never prints a newline cannot grow one without end. A longer line is dropped whole, nothing after it is handed on, and the watch throws line too large. The largest captured watch line is 1957 bytes. A watch line's posting carries a summary and contacts and never a body, so the ceiling is over 30 times that.
- **Watch buffer bound, 1024 watch lines** on the stream the app reads, **and 4096 raw lines** on the runner's stream behind it. The first is the real bound: an app 1024 lines behind a watch is not catching up. The second is a backstop that only fills when the decoding pump is behind the child, and it is set higher so the replayed lines a watch started with a since date prints before its first `ready` cannot trip it. That 4096 is deliberately generous and has not been measured against a real `hey watch --since` replay. Counted in the CLI's bytes, the worst case each bound can hold is, realistically, every line the size of the largest captured one, about 2 MB and about 8 MB, and adversarially, every line at the line ceiling, 64 MiB and 256 MiB.
- **What a reader that falls behind sees.** Both streams drop the line that did not fit and keep the ones already held, so what the app received is exactly what the CLI printed first, and the first casualty can never be a `ready` ahead of lines the app already has. The stream then throws watch fell behind and the child is terminated. The failure names the 1024 bound whichever buffer filled, and the runner's bound is never set below it, so the number stays true. Nothing is fabricated for what was dropped, no `resync` included: the app starts another watch, with a since date if it wants what it missed. A stream that ended because its reader was cancelled is not a reader that fell behind, and is neither failed nor terminated twice.
- **Termination grace, 5 seconds.** Stopping a child sends SIGTERM, then SIGKILL if its ending has still not arrived once the grace has passed. Nothing awaits the grace, so no call takes longer for it. The ending is checked again before the second signal, because the system hands a reaped child's identifier back out.
- **The fixture client is not bounded.** Its watch yields a whole fixture before anybody reads it, so a bound there would drop fixture lines from a test that never fell behind. An app stages watch fell behind with `script(watchFixture:thenFailing:)`.

## Considered options

- Hold each read to the output ceiling and hand on what fits. Rejected, for the half page it produces.
- Keep the newest lines when a watch falls behind. Rejected, because the app would be handed a stream with a hole in it and no way to tell where.
- Fill the hole with a synthesised `resync`. Rejected. The package reports what the CLI printed and nothing else, and a restarted watch already does what a resync asks for.
- Terminate once the read has returned. Rejected, because a child that never stops printing never lets it return.
- Bound only the client's watch stream, or only the runner's. Rejected. The pump yields into the client's stream without ever blocking, so bounding the runner's alone moves the growth there, and bounding the client's alone leaves the runner's growing whenever the child outruns the decoding.
- Put the limits in a mutable static a test overrides. Rejected, because suites run in parallel.
- Bound the fixture client's watch too. Rejected. It yields a whole fixture before anybody reads it, so a bound would drop fixture lines from a test that never fell behind. An app stages the failure with `script(watchFixture:thenFailing:)`, which yields the fixture's lines and then throws the failure it was given.

## What it costs

Three new cases on a public enum are source breaking for an exhaustive `switch`. That is acceptable before 1.0 and goes in the changelog, as does the fact that widening any of the three from a bare number to a payload later is source breaking again.

A genuinely huge page fails rather than loads. The package does not give page size a ceiling of its own to match, because a posting's size varies and the failure says exactly what happened.

An app that stops reading a watch for 1024 lines loses the watch and has to start another. That is the decision, not a side effect of it.

A sign in whose stderr passes the output ceiling is terminated and reported not completed with no stderr, since a login failure has no field that could say more. A CLI that writes 32 MiB of stderr during a sign in is already broken, so this is recorded rather than designed around.

The runner's 4096 line bound is a guess with generous headroom, not a measurement. If a real `hey watch --since` replay turns out to approach it, the number moves and the section on the numbers and their measurements moves with it.
