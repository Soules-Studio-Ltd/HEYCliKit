# Blocking pipe reads and the standard library Mutex are the package's two exceptions to Swift Concurrency

The package is Swift Concurrency only, and two things in it are not. Draining a child's pipes is a `read(2)` loop, and a blocking read must not sit on the cooperative pool: that pool has about one thread per core, and a watch waiting hours for its child to print a line would hold one of them for hours. Both drains therefore run on `DispatchQueue.global(qos: .userInitiated)` and resume a continuation at end of file, so the thread that blocks is one that exists to be blocked, and nothing above the runner sees Dispatch at all. The small state boxes in `ProcessRunnerLive` and `HEYFixtureClient` are held in the standard library's `Synchronization.Mutex` for a different reason: a `Process` termination handler, a `terminate` closure holding a pid and a `deinit` each reach that state from outside any isolation, and none of the three can await an actor. These two are the whole exception, written down here so it is not argued again at every call site.

Nothing else joins them. No Combine. No Foundation or POSIX locks, so no `NSLock`, `NSRecursiveLock`, `os_unfair_lock` or `pthread_mutex_t`. No `DispatchSemaphore`, no `DispatchGroup`, no queue of the package's own, and no `DispatchQueue.global` anywhere but those two reads. No `Thread`. Waiting is an `await`, work runs in a `Task` or on an actor, and state only tasks touch is actor isolated. The wait between SIGTERM and SIGKILL is a detached `Task` that sleeps rather than a Dispatch timer, so the termination escalation is not an exception either (ADR 0006). A third exception is a change to this decision, not a judgement made in a review.

What the exception costs stays contained: both drains are private functions in one file whose Dispatch call is the last statement before a continuation, and each mutex guards a value read and written in a few lines, never held across a suspension. The Dispatch half is retired when Foundation ships a pipe read that is genuinely asynchronous and ends when the task reading it is cancelled, since terminating a watch is exactly what `FileHandle.bytes` cannot do today. The Mutex half is retired when the runner no longer has to publish state from a synchronous callback. Either half goes on its own, and neither waits for the other.

## Considered options

- Run the blocking reads in a plain `Task` on the cooperative pool. Rejected because a watch's read blocks until its child writes, which is minutes or hours of a thread the pool cannot have back, and the stall that follows is the app's rather than the package's.
- Drain with `FileHandle.bytes` and hold no Dispatch at all. Rejected because it does not end when the task reading it is cancelled, and it does the same blocking read on a thread of Foundation's choosing rather than removing one.
- Put the state boxes behind an actor instead of a mutex. Rejected because a termination handler and a `deinit` are not async and cannot await one, so the value would reach the actor through a detached task that may not have run by the time it is read.

## Addendum: the sign in progress is a third file holding a mutex

The live client's login handle keeps its sign in progress, whether the app asked the sign in to stop and the outcome once it was decided, in a `Mutex` in `HEYClient.swift`, beside the runner and the fixture client. The reason is the same one. `LoginHandle.cancel()` is a synchronous public method, and a cancel also arrives through the task cancellation handler around the awaited outcome, which runs synchronously wherever the awaiting task was cancelled. Both reach that state from outside any isolation and neither can await an actor, while the flag a cancel sets has to be in place before the outcome is decided from it. The mutex guards a few lines and is never held across a suspension, exactly as the other two are. It is a third place that uses the Mutex half of this decision, not a third exception, so the decision itself is unchanged.
