# Changelog

All notable changes to HEYCliKit are recorded here. Versions are bare semver git tags. Releases before 0.5.0 predate this repository and have no tag here; 0.5.0 is its first commit.

## 0.6.0 - 2026-09-22

This release stops one row the CLI printed sparsely, or of a kind the package does not model, from failing the whole page, Screener list or watch line it sits in, makes optional the four fields where a zero value would have been a lie, makes every date decode on macOS 15, keeps every value out of a decoding failure's description, and says why a sign in was not completed.

- **A single posting's topic id is optional, source breaking.** `Posting.Single.topicID` was `TopicID` and is now `TopicID?`. The CLI derives a posting's `topic_id` from its app URL and leaves the key out when it has none, and `TopicID(0)` is a broken link rather than a topic, so a box read can now hand an app a row that names no topic instead of failing the page it sits on. An app unwraps it where it opened a topic from a row, and can still open the row itself through `appURL`. Inside a watch line nothing changes: the CLI prints no `topic_id` on a posting there and the line's own `thread_id` still fills it, so a change line's posting carries the topic it always did.
- **A posting's box id is optional, source breaking.** `Posting.Single.boxID`, `Posting.Bundle.boxID` and the `Posting.boxID` that forwards them were `BoxID` and are now `BoxID?`. The CLI leaves `box_id` out at zero and zero names no box. A box is asked for by its kind and never by this id, so an app that only reads a box reads nothing different.
- **A bundle's own URL is optional, source breaking.** `Posting.Bundle.bundleAppURL` was `URL` and is now `URL?`, since the CLI leaves `app_bundle_url` out when a bundle has no address of its own. The bundle's `appURL`, which opens its row, is unchanged and still required.
- **A Screener entry's topic id is optional, source breaking.** `ScreenerEntry.topicID` was `TopicID` and is now `TopicID?`, for the same reason as a posting's. An entry stands for the sender rather than for their mail, so approving and denying are unaffected, and an app that related an entry to a posting unwraps it.
- **A posting of any other kind, source breaking.** `Posting` gained a third case, `other(Posting.Other)`, for any `kind` besides `topic` and `bundle`, so an exhaustive `switch` over `Posting` no longer compiles until it handles `.other` or has a `default`. `Posting.Other` carries the fields every posting shares, read exactly as a single posting and a bundle read them, and `kind`, the CLI's own string verbatim, which is empty when the CLI printed no `kind` at all. The forwarding properties on `Posting` read an other posting as they read the other two, so a list that only shows a subject and a sender draws it unchanged. **This is a behaviour change**: a posting of any other kind used to fail the whole page, `entry` included even though hey-sdk's own schema declares it, and inside a watch it made an `added` or `updated` line `unrecognized`, which told an app nothing about a mail that had arrived. Both now decode, and the app decides whether and how to draw the row. A `kind` that is present but not text still fails the posting.
- **An absent key is the CLI's zero value.** The CLI leaves a key out instead of printing an empty string, a zero or an empty list, and the package required most of them. **This is a behaviour change**: `name`, `contacts`, `addressed_contacts` and `visible_entry_count` on a posting, `name`, `email_address`, `initials` and `avatar_background_color` on a contact, and `name`, `email_address`, `subject` and `summary` on a Screener entry now decode to `""`, `0` or `[]` where they used to fail the whole page, Screener list or watch line. The real world triggers are ordinary: a Bcc only or undisclosed recipients mail prints no `addressed_contacts`, a blank subject prints no `name`, a sender whose name has no letters prints no `initials`, and a sender HEY knows only by a bare address prints neither `name` nor `summary`. It mattered most on a watch: a decoding failure anywhere inside a line made the whole line `unrecognized`, so an `added` line for a Bcc only mail told an app nothing at all, and it now arrives as the change it is. `app_url`, `active_at` and `observed_at` stay required, and so do the `id` of a posting, a contact and a Screener entry: a row the app cannot open, that HEY never observed, or that has no identity, is not a row.
- **Every date decodes on macOS 15.** The package read dates with the `.iso8601` strategy, and under it the Foundation that macOS 15 ships refuses fractional seconds. Every `observed_at` and every watch line's `at` carries one, so on the package's minimum OS every page read failed and every watch line, `ready` included, was `unrecognized`. The shared decoder behind every read and every watch now splits the fraction off itself, parses the rest and adds the fraction back, for anywhere from none to nine digits, and keeps `Z` and a local offset such as `+02:00`, which is what `expires_at` carries. On current macOS every date decoded already, and the one visible change there is that a date the package cannot read is now described in the package's own words, which name the field's path and never carry the value. Only the current Foundation was checked, on macOS 26, because no iOS 18 simulator runtime or macOS 15 machine was available. Nothing was run on the older Foundation. The claim for it rests on reading its parser's source in swift-foundation's release/6.0 branch, which shows it reads the date the decoder hands it once the fraction is taken out, `Z` and `+02:00` included.
- **A refused row is dropped and counted.** `BoxPage` gained `refusedRowCount`. A row the package cannot read at all, one with no `id`, `app_url`, `active_at`, `observed_at` or `creator`, an id that is not an integer, or a row that is not an object, is dropped from the page and counted there. **This is a behaviour change**: such a row used to fail the whole page. `postings.count + refusedRowCount` is how many rows the CLI printed, so an app comparing the decoded count against the page size it asked for sees one fewer per refused row, and the cursor is unaffected because it is opaque. A page whose `postings` is absent or not a list still fails as a whole. A watch line whose posting is refused this way is still `unrecognized`, since a line holds one posting and there is no page to count it against.
- **A decoding failure's description never carries a value.** `DecodingFailure.description` now names keys, positions and schema tokens only, so an app may log it verbatim without writing anything out of the mailbox to disk. It used to be Foundation's own description of the decoding error, which quotes the character it could not parse, the number it could not represent and the raw value an enum could not read, and a mail account missing a field was described with its id. It is now one of a few sentences in the package's own words, such as `Expected String at data[1].version.`, `The key postings is missing at data.`, `The value at data[0].status could not be read.` or `The output could not be read.`, the last for output that is not JSON and for a number Foundation cannot represent, which it reports at the root even inside valid JSON, and a value the package refuses on purpose, such as a date or a mail account missing its email address, is described by the refusal alone. **This is a wording change**: an app that asserted Foundation's phrasing, in a test or anywhere else, sees it change. The CLI's own text is still carried whole in `rawText`, which is unchanged.
- **A sign in that was not completed says why.** `LoginFailure` gained `kind`, a `CaseIterable` `LoginFailure.Kind` that is `timedOut`, `accessDenied`, `cancelled` or `notClassified`, so an app can tell the CLI's own five minute timeout from a sign in the user declined without reading the CLI's text, which carries the sign in address. The package decides it: a cancel the app asked for is `cancelled` whatever ending the child came to afterwards, and otherwise exit 3 with the failed envelope's error on stderr reads as timed out or access denied, checked against the CLI's source at 1.4.0, 1.4.3 and 1.6.0. Everything else, a stderr the package stopped past the output ceiling included, is `notClassified`. `init(exitStatus:standardError:)` keeps its signature and classifies the ending by the same rule, never as `cancelled`, since an ending alone cannot say a cancel was asked for, and `init(exitStatus:standardError:kind:)` is added to state any kind. `HEYFixtureClient` gained `script(loginNotCompleted:)`, which scripts a sign in ending with any kind, and a scripted cancel resolves as `cancelled` by the same rule as a live one. **This is a behaviour change**: `kind` takes part in equality, so a test that compared a cancelled sign in against a failure built with the two argument initialiser now states `kind: .cancelled`. Adding a kind later is a source break for an exhaustive `switch`, as adding an error case is, so a new kind waits for a version that is allowed to break.
- **A sign in failure's description never carries its stderr.** `LoginFailure` is now `CustomStringConvertible`, and its description names the kind and how the child ended, such as `The sign in timed out (exit code 3).`, and nothing read from stderr, so an app may log it verbatim. A `LoginOutcome` is described through it, so an outcome logged as it is carries no stderr either. **This is a behaviour change**: the description used to be Swift's own, which printed `standardError` in full, and with it the sign in address and the machine's install id. The stderr itself is unchanged and still carried whole for the app's local logs. The conformance is source breaking only for an app that declared its own `CustomStringConvertible` conformance on `LoginFailure`, which it now removes.

## 0.5.0 - 2026-09-18

This release makes every source break the public surface needed while the package is at 0.x, keeps the CLI's words when a failure is printed on stderr, and lets the fixture client fail a watch after its lines.

- **A labelled non empty set initialiser, source breaking.** The failable initialiser taking a sequence was `NonEmptySet.init?(_:)` and is now `init?(elements:)`. The unlabelled spelling read as the variadic initialiser, so where nothing fixed the element type, `NonEmptySet(ids)` compiled and built a set holding one array. An app that builds a set from an array or another sequence writes `NonEmptySet(elements: ids)`, and the variadic spelling is unchanged.
- **Cancelling a sign in is a method.** `LoginHandle.cancel` was a public stored closure and is now `cancel()`. A call such as `handle.cancel()` compiles unchanged.
- **A sign in's outcome is a property, source breaking.** `LoginHandle.outcome` was a stored closure awaited as `await handle.outcome()` and is now read as `await handle.outcome`. An app drops the parentheses. It is still decided once and shared, and cancelling the task that awaits it still cancels the sign in.
- **Releasing a held answer is a method.** `HEYHeldAnswer.release` was a public stored closure and is now `release()`. A call such as `held.release()` compiles unchanged, and a release is still a latch.
- **The unreadable watch line is spelled the American way, source breaking.** `WatchLine.unrecognised(rawText:)` is now `WatchLine.unrecognized(rawText:)`. An app renames the case wherever it matches it, and what it carries is unchanged.
- **A failed envelope on stderr keeps the CLI's words.** When a command or a watch fails and stdout is not an envelope, stderr is now read as one, and a failed envelope there decides the meaning by the same rule as one on stdout, keeping the CLI's `code`, `error` and `hint`. **This is a behaviour change**: hey 1.4.0 prints a signed out read's envelope on stderr with nothing on stdout, so `HEYCliKitError.signedOut` now carries the CLI's hint where it used to carry none. A child killed by a signal is still a process failure, a clean exit still never reads stderr, a success envelope on stderr is not read as one, and stderr holding an envelope followed by other text still falls through to the exit code. This corrects the 0.1.0 note that the CLI's details are carried only when it printed them on stdout.
- **A scripted watch can fail after its lines.** `HEYFixtureClient` gained `script(watchFixture:thenFailing:)`, `script(watchStandardOutput:thenFailing:)` and their twins `scriptRepeating(watchFixture:thenFailing:)` and `scriptRepeating(watchStandardOutput:thenFailing:)`. Each stages a watch that yields its lines exactly as a plain scripted watch and then throws the given error from the stream, which is where the live client reports a watch that fell behind, a line too large and too much output. They are watch only, like the login spellings, and have no held form, since a hold only delays the call that opens the stream. This corrects the 0.4.0 note that an app stages `watchFellBehind` by scripting a failing watch: that throws from the call that opens the watch, before any stream exists, so an app stages it with `script(watchFixture:thenFailing:)` or its raw bytes twin instead.
- **A fake credential instant.** The signed in auth status fixture's `expires_at` now reads `2026-01-01T00:00:00Z`, and the package's scrub check fails on any `expires_at` in a committed fixture holding another instant. Only a test that asserts the expiry decoded from `auth-status.json` has to change. Other capture timestamps stay as captured on purpose, as the fixtures README explains.
- **Public documents.** CONTRIBUTING and SECURITY are added at the root and linked from the README, and the README's `--json` design rule now names the login exception. ADR 0007 records that identifiers are American, prose is British, and Swift's own spellings such as `cancelled` win where they differ. ADR 0008 records that a published tag is never moved or deleted, and that a wrong release gets a patch version instead. ADR 0006 now carries the measurements behind every ceiling, ADR 0004 names the sign in progress as a third file holding a mutex, and the glossary defines a private capture.

## 0.4.0 - 2026-09-12

- **A misbehaving child has ceilings.** The live client holds every `hey` child to three ceilings, and passing one is a failure of its own rather than a short answer. A one shot command that writes more than 32 MiB on stdout or stderr is terminated and throws `HEYCliKitError.outputTooLarge(limitInBytes:)`, never an envelope cut short for the decoder to turn into a page that looks whole. A watch line longer than 64 KiB is dropped whole, the child is terminated and the stream throws `HEYCliKitError.lineTooLarge(limitInBytes:)`, because a partial line is not a watch line. A watch child whose stderr passes 32 MiB ends the stream with `outputTooLarge` too, rather than with the signal the package sent it, and a sign in whose stderr passes it is not completed, whatever its child's exit. The numbers, and why each is the one it is, are in ADR 0006.
- **The watch buffer is bounded.** `watch(_:since:)` used to buffer without bound. Its stream now holds 1024 watch lines for a reader that has not taken them, with 4096 raw lines inside the runner behind it. **This is a behaviour change**: an app that stops reading for that long is sent the lines already held, exactly as the CLI printed them, then `HEYCliKitError.watchFellBehind(limitInLines:)`, and the child is terminated. The number is 1024 whichever of the two buffers filled. The line that did not fit is the one dropped, so what the app has is a true prefix and the first `ready` is never the casualty. Nothing is synthesised in place of what was dropped, no `resync` included: the app starts another watch, with a since date if it wants what it missed.
- **Stopping a child insists.** Cancelling an operation, dropping a watch's stream and cancelling a sign in still send SIGTERM, and a child that has not ended five seconds later is now sent SIGKILL, so a CLI that ignores the signal can no longer outlive the app's request for ever. Nothing awaits the grace, so no call takes longer for it, and it is not a timeout: an operation still has no deadline, and a sign in still waits for the user until the app cancels it. `LoginOutcome` is decided exactly as before, so a sign in killed after its cancel is not completed, as one that died on SIGTERM never was.
- **A sign in's stdout is discarded.** The login child's stdout now goes to `/dev/null` instead of into a buffer nobody read, so a chatty CLI can never end a sign in for filling it. The package never read that envelope, so nothing an app sees changes.
- **Three new error cases, source breaking.** `outputTooLarge(limitInBytes:)`, `lineTooLarge(limitInBytes:)` and `watchFellBehind(limitInLines:)` are added to `HEYCliKitError`, so an exhaustive `switch` over it no longer compiles until it handles them or has a `default`. Each carries its ceiling as a plain labelled number, and an app can build one to stage through the fixture client. Giving one of them a payload struct later, to carry more than that number, would be source breaking in its own right. The fixture client's watch still buffers without bound, since it yields a whole fixture before anybody reads it, so an app stages `watchFellBehind` by scripting a failing watch.
- **Scrubbed paging cursors.** The paging cursors in the fixtures are re-encoded, so every one of them now matches the fake data the rest of the fixtures use. **Nothing about the package's behaviour changes**: a `Cursor` is read and never parsed, so a cursor is opaque to every operation and only a test that asserts a cursor's exact `rawValue` against the fixtures has to be re-derived. The fixtures README's scrub rule now names cursors, and a check in the package's own suite inspects every cursor in the committed fixtures and fails on any that has not been scrubbed. The check matters more than the re-encode: raw captures land in this repository under a `-private` suffix as a matter of course, so without it the next capture could repeat the miss.

## 0.3.0 - 2026-09-12

- **The child environment is an allowlist.** A spawned `hey` child no longer inherits the app's environment. It gets four keys copied from it when they are set, `TMPDIR`, `LANG`, `LC_ALL` and `LC_CTYPE`, a `HOME` pinned to the user's own home folder and a `PATH` pinned to `/usr/bin:/bin:/usr/sbin:/sbin`, then the extra environment passed to `HEYClient.live(executable:accountSelection:environment:)`, then `HEY_NONINTERACTIVE` settled last exactly as before. Everything else is dropped, `HEY_*` included. **This is a behaviour change for any app that relied on inheritance**: the extra environment is now overlaid on that fixed allowlist rather than on the whole process environment, so a variable an app was counting on the child receiving has to be passed through `environment:` explicitly. The extras themselves are unchanged and are still honoured verbatim, `HEY_*` keys included, so an app that genuinely needs a proxy or a cache directory says so and gets it. The reason is that the CLI takes its most important settings from the environment: `HEY_BASE_URL` and `HEY_CABLE_URL` choose the host, `HEY_TOKEN` and `HEY_AT` hand it credentials, `HEY_NO_KEYRING` moves the ones it holds into a plaintext file, and `HOME` and `XDG_CONFIG_HOME` choose the config directory whose file carries a `base_url` of its own. A single `launchctl setenv` writes the GUI session's environment for every app the user launches afterwards, and because the CLI keys its keychain item on the base URL, a redirected host reads as signed out, which walks the user into a fresh sign in against that host with their real password. `HOME` and `PATH` are pinned rather than dropped because the child still needs both: the working directory is the home folder either way, and login opens the sign in page with a bare `open` it searches for. The pinned `PATH` is the value launchd already hands a Finder launched app, so for the way the apps are actually started nothing changes. ADR 0005 records the decision and what it costs.

## 0.2.0 - 2026-09-12

- **Repeating fixture answers.** `HEYFixtureClient` gained `scriptRepeating(_:fixture:exitCode:standardError:)`, `scriptRepeating(_:standardOutput:exitCode:standardError:)` and `scriptRepeating(_:failing:)`, the same three spellings as `script`, for the answer an operation falls back to once its queue is empty. It is for the operations that merely happen around the one a test is about: an app that polls the Screener on a timer no longer needs one scripted answer per tick, counted by hand, in every test of something else. Queued answers still come first and in order, a fallback is never used up, scripting a second one for an operation replaces the first, an operation with neither a queue nor a fallback still fails with `HEYFixtureClientError.notScripted`, and every call is recorded and yielded exactly as before. Login has no repeating spelling, since a sign in is a one shot flow the user starts rather than something an app polls.
- **Held fixture answers.** `HEYFixtureClient` gained `scriptHeld(_:fixture:exitCode:standardError:)`, `scriptHeld(_:standardOutput:exitCode:standardError:)` and `scriptHeld(_:failing:)`, the same three spellings again, for an answer that does not resolve until the test releases it. Each returns a `HEYHeldAnswer` whose only member is `release`, and nothing else releases it. It exists because a client whose every operation answers at once leaves the interleaving between two calls in flight unreachable: a consumer cannot build a client with a slow closure of its own, so a mutation the CLI confirms while a read lands underneath it could not be tested at all. A held call is recorded and yielded as an invocation the moment it arrives, and leaves its operation's queue then, so the next call to that operation reads the next answer while the first still waits. Releasing is a latch and not a signal: a release that lands before its call is remembered and the call answers at once, so a release is never lost by arriving early. To reach an interleaving rather than merely release safely, make the held call from a task the test owns, await its invocation, then release and await that task. A second release is a no op. Cancelling the task that awaits a held call throws `CancellationError`, the error a live client reports a cancelled operation with, and that is the one place a held answer and a plain one differ, since a plain scripted answer still resolves whether or not its task was cancelled. Nothing checks cancellation after the wait, so a release followed by a cancel answers and a cancel followed by a release throws, neither of them depending on scheduling. A cancel and a release that have both landed before the call reaches the hold answer, because the release is read first. Whatever was held is decoded and mapped exactly as the same answer scripted plainly, so holding changes when a call answers and never what it answers. `scriptHeld` is not `@discardableResult` on purpose: a handle nobody keeps is an answer nobody can release, and the unused result warning is the only diagnostic there is.

## 0.1.0 - 2026-09-05

The first release: a typed Swift client over the `hey` executable an app supplies, the models it decodes, the watch stream, the error mapping, and a test support product built on captured CLI output.

- **The client.** `HEYClient` is a `Sendable` struct with one public method per operation, built with `HEYClient.live(executable:accountSelection:environment:)`. There is no other way to build one, apart from the fixture client in the test support product, so an added operation is never a source breaking change. The app hands the package the location of a `hey` executable and the package never searches for one. The `AccountSelection` is fixed when the client is built, so a change made in the user's terminal cannot alter what the app sees. Every command carries `--json` and that selection, runs with `HEY_NONINTERACTIVE` from the user's home folder with stdin at `/dev/null`, and the human readable output is never parsed.
- **Reads.** `signInStatus()`, `version()`, `mailAccounts()`, `boxPage(_:pageSize:cursor:)` and `screener()`. A box read returns a `BoxPage` of typed postings with the cursor that reads the next page. The Screener carries the envelope's `meta.total_count`, the only meta field the package reads, so a list without one is a decoding failure rather than a count guessed from the entries. `signInStatus()` is the one operation that answers rather than throws while the CLI is signed out: `hey auth status` exits 0 and prints a success envelope either way, so an app that asks it first is handed a status with `isSignedIn` false. Every other command exits 3 while signed out, and its operation throws `HEYCliKitError.signedOut` instead, which is why the status is the call an app makes first.
- **Mutations.** `approveScreenerEntries(_:)` and `denyScreenerEntries(_:)` report what HEY confirmed. `move(_:to:)`, `markSeen(_:)` and `markUnseen(_:)` return nothing, because HEY confirms a write with a summary alone. Each takes a `NonEmptySet` of ids, so a call that would change nothing cannot be made, the ids reach the command line in the order they were given, and nothing is ever retried.
- **The watch.** `watch(_:since:)` follows a non empty set of box kinds as a long lived child and returns an `AsyncThrowingStream` of `WatchLine`, one element per line the CLI prints, buffered without bound so a ready is never dropped. An optional since date is passed as `--since` in ISO 8601, and the CLI's calendar lines are never asked for. A `change` value or a line body this version cannot read arrives as `WatchLine.unrecognised` carrying the CLI's own text, and never ends the watch. Cancelling the task that reads the stream, or dropping it, sends SIGTERM and ends the stream without throwing. A clean exit ends it normally, and any other ending throws the same mapped error every other operation throws.
- **Login and logout.** `login()` starts the CLI's own sign in flow and returns a `LoginHandle` carrying `cancel` and `outcome`. The package runs it only because the app asked, never on its own initiative and never as a retry. That spawn carries neither `--json`, `--account` nor `HEY_NONINTERACTIVE`, since the CLI opens a browser and talks to the user itself, and the envelope it prints is never read. There is no timeout: a sign in waits until the app stops it. `outcome` can be awaited from more than one place and is decided once. Exit 0 that nobody cancelled is `LoginOutcome.completed`. Every other ending, and every ending at all once `cancel` was called, is `notCompleted` carrying a `LoginFailure` with the child's ending and its stderr, because SIGTERM is a request a CLI is free to answer with a clean exit and a sign in the app stopped is never a completed one. `logout()` is an ordinary one shot mutation.
- **Errors.** `HEYCliKitError` with signed out, HEY unreachable or failed, not found, usage, rate limited, unknown code, decoding failure and process failure cases, each carrying the CLI's raw `code`, `error` and `hint` as opaque text when it printed them on stdout. A well formed error envelope decides the meaning before the exit code does, so an exit code the package does not know keeps the CLI's own words. A child killed by a signal is a process failure whatever it printed, and stdout that is not an envelope at exit 3 is still signed out. A cancelled operation throws `CancellationError` rather than reporting the child it terminated. `CLIErrorDetails`, `DecodingFailure`, `ProcessFailure` and `LoginFailure` have public initialisers, so an app can build a failure to stage through the fixture client or to test what it presents, including a process that never launched. `ProcessExitStatus` says whether a child exited with a code or was killed by a signal.
- **Models and value types.** `SignInStatus`, `CLIVersion`, whose `commit` and `date` are optional because a binary built from source stamps them as `unknown` or leaves them out, `MailAccount`, `BoxPage`, `Posting` with its `single` and `bundle` cases, `Contact`, `Screener`, `ScreenerEntry`, `ScreenerDecision`, `ScreenerApproval` and `WatchLine` with its `Change` and `Deletion`. A posting's `subject` is the CLI's `name`, the subject line of its topic or the bundle's title, and `isSeen` is the CLI's `seen`, which is unseen when the CLI omits it. Beside them: `NonEmptySet`, which drops duplicates and keeps the order it was built in for the command line while comparing and hashing on its members alone; `PageSize`, which accepts 30 and every larger multiple of 10 and rejects anything else at construction; `Cursor`, which is read but never parsed and only ever handed back; `BoxKind`, which is how a box is named everywhere and is `Decodable`, so a box the CLI lists is read through it rather than as a bare string; and the ids `Posting.ID`, `BoxID`, `TopicID`, `Contact.ID`, `ScreenerEntry.ID` and `MailAccount.ID`. `HEYCliKit.testedCLIVersion` is the CLI version the fixtures were captured from, currently 1.4.0.
- **Test support.** A second library product, `HEYCliKitTestSupport`, ships the captured CLI output. `HEYFixtures.data(named:)` reads one fixture by file name, never through a resource bundle directly, and after 1.0 those file names are part of the public API: a rename goes in the changelog. `HEYFixtureClient` builds a `HEYClient` that answers from a queue per operation, fails an unscripted call with `HEYFixtureClientError.notScripted`, and reports every call as a `HEYClientInvocation` carrying that operation's own parameters, on an `AsyncStream` and in `recordedInvocations`. Scripted bytes go through the package's own envelope decoding and error mapping, so a test sees exactly what the live client would have returned or thrown. A watch replays a shipped ndjson fixture one line per element and ends by the scripted exit code, and a login is scripted with an outcome or left pending until the app cancels it.
- **Requirements.** macOS 15 or later, Swift 6 language mode, tools version 6.0 so Xcode 16 can still build it, and no third party dependencies. The app supplies the `hey` executable.
